## 1. First Fit vs Best Fit: Worked Example

### Given

- Initial free holes: `150 KB` and `350 KB`.
- Process requests arrive in this order: `300 KB`, `25 KB`, `125 KB`, `50 KB`.
- Allocation is **contiguous**: each process must fit in one hole.
- When a process is allocated from a hole, the unused remainder stays available as a smaller hole.

### First Fit

**Rule:** Starting from the beginning of the free list/memory, allocate each process to the first hole large enough to contain it.

| Process | Request | Hole selected | Remainder |
|---|---:|---:|---:|
| P1 | 300 KB | 350 KB | 50 KB |
| P2 | 25 KB | 150 KB | 125 KB |
| P3 | 125 KB | 125 KB | 0 KB |
| P4 | 50 KB | 50 KB | 0 KB |

**Result:** All four requests can be satisfied using First Fit.

### Best Fit

**Rule:** Choose the smallest hole that is large enough for the process. This minimizes the immediate leftover space for that allocation; it does not guarantee the best overall memory use.

| Process | Request | Hole selected | Remainder |
|---|---:|---:|---:|
| P1 | 300 KB | 350 KB | 50 KB |
| P2 | 25 KB | 50 KB | 25 KB |
| P3 | 125 KB | 150 KB | 25 KB |
| P4 | 50 KB | Cannot fit | — |

After P1, P2, and P3, the free holes are `25 KB` and `25 KB`. P4 needs `50 KB`, so it cannot fit into either hole even though the total free space is `50 KB`.

**Result:** Best Fit cannot satisfy all four requests. This is an example of **external fragmentation**.

### Worst Fit for the same example

**Rule:** Choose the largest available hole each time.

| Process | Request | Hole selected | Remainder |
|---|---:|---:|---:|
| P1 | 300 KB | 350 KB | 50 KB |
| P2 | 25 KB | 150 KB | 125 KB |
| P3 | 125 KB | 125 KB | 0 KB |
| P4 | 50 KB | 50 KB | 0 KB |

**Result:** All four requests can be satisfied using Worst Fit in this example.

> **Exam tip:** Process requests must be handled in the given order unless the question explicitly says otherwise. After each allocation, update the size of the remaining hole(s).

## 2. Allocation Algorithms — Quick Comparison

| Algorithm | Rule | Search behaviour | Common point to remember |
|---|---|---|---|
| First Fit | First hole large enough | Starts at the beginning; stops at the first suitable hole | Usually simple and fast |
| Next Fit | First suitable hole found after the last allocation point | Continues from the previous allocation position | Does not restart from the beginning each time |
| Best Fit | Smallest hole large enough | Usually examines all holes unless the list is specially organized | Can create many small holes |
| Worst Fit | Largest available hole | Usually examines all holes unless the list is specially organized | Leaves the largest remainder after an allocation |

- These algorithms are commonly discussed with **variable/ dynamic contiguous partitioning**.
- First Fit, Next Fit, Best Fit, and Worst Fit do **not** eliminate external fragmentation.
- No algorithm is universally best; results depend on the request sequence and memory layout.

## 4. Contiguous vs Non-Contiguous Allocation

### Contiguous allocation

- Each process must occupy one continuous physical-memory region.
- A process cannot be split across separate holes in basic contiguous allocation.
- Fixed partitioning and variable partitioning are examples.
- External fragmentation can prevent allocation even when the total free memory is sufficient.

### Non-contiguous allocation

- A process can be divided into parts and its parts can occupy different physical-memory locations.
- Paging is a major non-contiguous allocation technique.
- It allows a process to use free frames located in different parts of RAM.

## 5. Paging: Core Concepts

Paging divides memory into equal-sized units:

- **Page:** A fixed-size block of a process's logical/virtual address space.
- **Frame:** A fixed-size block of physical memory (RAM).
- **Page table:** Maps each virtual page of a process to a physical frame.

### Essential rules

- **Page size = frame size.**
- A process is divided into pages; RAM is divided into frames.
- A page can be placed in any available frame; the process's pages do not need to occupy consecutive frames.
- A page table records the frame number containing each page.
- The **Memory Management Unit (MMU)** translates logical/virtual addresses into physical addresses using the mapping information.
- Paging removes **external fragmentation in physical frame allocation**, because any free frame can hold any page.
- Paging can still cause **internal fragmentation**, especially in the last page of a process if the process size is not a multiple of the page size.
- Page tables consume memory.

### Example

Suppose:
- Process size = `4 bytes`
- Page size = `2 bytes`

Then:

`Number of pages = Process size / Page size = 4 / 2 = 2 pages`

The pages are numbered from `0` to `1`.

If physical memory is `16 bytes` and frame size is `2 bytes`:

`Number of frames = Physical memory size / Frame size = 16 / 2 = 8 frames`

The frames are numbered from `0` to `7`.

If page 0 is in frame 2 and page 1 is in frame 4, the process's pages occupy non-consecutive physical memory.

## 6. Logical Address Translation in Paging

A logical address is divided into two fields:

- **Page number (p):** Identifies the page.
- **Page offset (d):** Identifies the byte within that page.

The page table maps the page number to a frame number. The offset stays the same during translation.

The physical address is made of:

- **Frame number (f)**
- **Frame offset (d)**

Thus:

`Logical address (page number, offset) → Page table → Frame number`

`Physical address = (frame number, same offset)`

### Address translation formulas

Let:
- `LA` = logical address, measured in bytes
- `page_size` = size of one page in bytes
- `p` = page number
- `d` = page offset

Then:

`p = floor(LA / page_size)`

`d = LA mod page_size`

If the page table maps page `p` to frame `f`, then:

`Physical address = f × frame_size + d`

Since `page_size = frame_size`, the offset `d` is unchanged.

### Bit counts

If page size is `2^d` bytes:
- Page-offset bits = `d`.

If logical address space has `2^m` byte-addressable locations:
- Logical-address bits = `m`.
- Page-number bits = `m − d`.
- Number of pages = `2^(m − d)`.

If physical memory has `2^n` byte-addressable locations:
- Physical-address bits = `n`.
- Frame-number bits = `n − d`.
- Number of frames = `2^(n − d)`.

## 7. Worked Address-Space Example

### Given

- Logical address space = `4 GB`
- Physical address space = `64 MB`
- Page size = `4 KB`
- Assume byte-addressable memory and binary units: `1 KB = 2^10 bytes`, `1 MB = 2^20 bytes`, `1 GB = 2^30 bytes`.

### Step 1: Logical address bits

`4 GB = 4 × 2^30 bytes = 2^32 bytes`

Therefore:

- Logical-address bits = `32`
- Logical address = `page number + page offset`

### Step 2: Page-offset bits

`4 KB = 4 × 2^10 = 2^12 bytes`

Therefore:

- Page-offset bits = `12`

### Step 3: Number of pages

`Page-number bits = 32 − 12 = 20`

`Number of pages = 2^20`

### Step 4: Physical address bits

`64 MB = 64 × 2^20 bytes = 2^26 bytes`

Therefore:

- Physical-address bits = `26`

### Step 5: Number of frames

Frame size equals page size, so frame size = `4 KB = 2^12 bytes`.

`Frame-number bits = 26 − 12 = 14`

`Number of frames = 2^14`

### Step 6: Number of page-table entries

In a simple single-level page table with one entry per virtual page:

`Number of entries = Number of pages = 2^20`

### Step 7: Page-table size (frame number only)

Each entry must store a frame number. There are `2^14` frames, so the frame number requires `14 bits`.

`Page-table size = Number of entries × bits per entry`

`= 2^20 × 14 bits`

`= 14,680,064 bits`

`= 1,835,008 bytes`

`≈ 1.75 MiB`

This is the **minimum size when each entry stores only the frame number**. Real page-table entries usually include extra bits, such as valid/present, protection, referenced, and dirty/modified bits, so the actual size can be larger.

### Final answer table

| Quantity | Answer |
|---|---:|
| Logical-address bits | 32 bits |
| Page-offset bits | 12 bits |
| Page-number bits | 20 bits |
| Number of pages | `2^20` |
| Physical-address bits | 26 bits |
| Frame-offset bits | 12 bits |
| Frame-number bits | 14 bits |
| Number of frames | `2^14` |
| Page-table entries | `2^20` |
| Minimum page-table size (frame number only) | `14 × 2^20` bits = `1,835,008 bytes` ≈ `1.75 MiB` |

## 8. GATE Quick Revision

- **First Fit:** First hole that is large enough.
- **Next Fit:** First suitable hole found from the last allocation point.
- **Best Fit:** Smallest hole that is large enough.
- **Worst Fit:** Largest available hole.
- **External fragmentation:** Total free memory may be enough, but no single contiguous hole is large enough.
- **Paging:** Splits a process's virtual address space into pages and RAM into frames.
- **Page size = frame size.**
- **Page table:** Maps page numbers to frame numbers.
- **MMU:** Performs address translation.
- **Logical address:** Page number + page offset.
- **Physical address:** Frame number + frame offset.
- **Offset bits:** `log₂(page size in bytes)`.
- **Number of pages:** `Logical address space / page size`.
- **Number of frames:** `Physical memory size / frame size`.
- **Page-table entries:** Usually one per virtual page in a simple single-level page table.
- **Minimum page-table size:** `Number of entries × bits needed to store a frame number` (plus any additional entry bits in a real system).
